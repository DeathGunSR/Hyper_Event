## ۳. معماری تحویل‌شده

```
هلو (فقط خواندنی)
   └─ HolooDb: GetNewInvoicesAll / GetInvoiceCodesForDay / وااترمارک
        └─ SyncAgent (پس‌زمینه، هر ۳۰ ثانیه)
             ├─ LocalStore v4: Invoices + SyncQueue + Meta
             │    (صف پایدار، وضعیت review، PopupShown، ServerStatus)
             └─ ApiClient: HMAC-SHA256 + HttpWebRequest (سازگار با .NET 4.0)
                  └─ EbiCampaign API (ASP.NET Core / .NET 10)
                       └─ SQL Server: Rounds / Invoices / IngestRequests / AuditLog
```

- سرور به هلو دسترسی ندارد و هیچ نوشتنی در هلو انجام نمی‌شود.
- صندوق در قطعی شبکه کار خود را ادامه می‌دهد؛ فاکتورها در صف SQLite می‌مانند و با backoff دوباره ارسال می‌شوند.
- پاپ‌آپ تخفیف با `PopupShown` در دیتابیس محلی تکرار نمی‌شود (حتی پس از ری‌استارت).

## ۴. پیاده‌سازی

### ۴.۱. سرور کمپین (`server/EbiCampaign.Api`)

| بخش | جزئیات |
|---|---|
| اسکیما | `Rounds`، `Invoices`، `IngestRequests`، `AuditLog` + `SchemaVersions` |
| یکتایی | `UNIQUE(SourceId, FCode)` — یک فاکتور در هیچ دوره‌ای دوبار ثبت نمی‌شود |
| دورهٔ باز | ایندکس یکتای فیلترشده روی `Status='Collecting'` — فقط یک دورهٔ باز |
| شمارش | قفل `UPDLOCK, HOLDLOCK` روی دوره و فاکتور؛ آزمون دو عامل هم‌زمان، مرز ۱۰۰۰ و فاکتور تکراری هم‌زمان |
| تکمیل | با رسیدن به `Target` وضعیت `Completed` می‌شود؛ دورهٔ بعد خودکار باز **نمی‌شود** |
| Held | فاکتور معتبر وقتی ظرفیت ندارد `Held` می‌شود و فقط با تخصیص صریح مدیر وارد دوره می‌شود |
| ایدمپوتنسی | `RequestId` + هش بدنه؛ پاسخ کش‌شده؛ استفادهٔ مجدد با بدنهٔ دیگر `409` |
| ابطال | `POST .../void` با دلیل؛ در دورهٔ باز شمارنده کم می‌شود، در دورهٔ بسته فقط `NeedsReview` |
| گزارش مشکوک | `status:"review"` از عامل: خروج از شمارندهٔ دورهٔ باز + `NeedsReview` |
| موبایل/امتیاز | اولین شماره برنده است؛ شمارهٔ متفاوت `conflict`؛ امتیاز در سرور محاسبه می‌شود |
| امنیت | HMAC-SHA256، پنجرهٔ ۳۰۰ ثانیه، مقایسهٔ ثابت‌زمان، `X-Admin-Key`، محدودیت حجم بدنه |
| حسابرسی | `AuditLog` برای شروع/بستن دوره، ابطال، بررسی، تخصیص و به‌روزرسانی موبایل |
| SQL | تمام کوئری‌ها پارامتری؛ هیچ SQL داینامیک از ورودی |

مسیرهای مدیریتی فقط با `X-Admin-Key` کار می‌کنند. کلید پیش‌فرض از `appsettings.json` حذف شد؛ بدون تنظیم کلید،
مسیرهای مدیر `503` و بدون امضای معتبر، ingest `401` می‌دهد.

### ۴.۲. عامل همگام‌سازی (`posdiscount/src/SyncAgent.cs`)

- خواندن **همهٔ صندوق‌داران** از جدول روز + آرشیو از تاریخ شروع کمپین.
- وااترمارک پایدار `SyncLastFCode` در `Meta`؛ در اولین اجرا از کمترین کد معتبر پس از شروع کمپین.
- هر فاکتور خوانده‌شده — حتی اگر از قبل در دیتابیس محلی باشد — یک بار در صف قرار می‌گیرد؛
  این «backfill» تضمین می‌کند ۱۴۵ فاکتور قدیمیِ نصب فعلی پس از فعال‌سازی همگام‌سازی از شمارش عقب نمانند.
- دسته‌بندی ۱..۵۰۰ (پیش‌فرض ۱۰۰) و حداکثر ۵۰ دور در هر چرخه برای جلوگیری از حلقهٔ بی‌پایان.
- صف پایدار با `Attempts`، `NextTryAt` و `LastError`؛ backoff نمایی تا ۳۰۰ ثانیه.
- تطبیق روزانه (حداکثر هر ۶۰ دقیقه): کدهای معتبر روز کاری از هلو خوانده می‌شود؛ فاکتور محلی غایب
  یک بار `review` و وارد صف می‌شود (تکرار ساعتی صف را پر نمی‌کند).
- قفل اجرای هم‌زمان (`Monitor.TryEnter`) تا دو چرخه هم‌زمان یک صف را نفروشند.
- هیچ نوشتنی در هلو ندارد؛ `HolooDb` فقط `SELECT`.

### ۴.۳. دیتابیس محلی (`LocalStore`)

- نسخهٔ اسکیما ۴: ستون‌های `Status`، `MobileEnteredBy`، `MobileEnteredAt`، `PopupShown`، `ServerStatus`
  و جدول `SyncQueue`.
- مهاجرت نرم با `EnsureColumn`؛ دادهٔ قبلی حفظ می‌شود.
- ثبت «چه کسی شماره را وارد کرد» (`MobileEnteredBy`) برای حسابرسی.
- `EnqueueSync` فقط وقتی دادهٔ مؤثر عوض شود؛ `SetMobile` همیشه صف را به‌روز می‌کند.
- مالکیت شماره: تغییر شماره در سرور فقط با مدیر؛ در صندوق، شمارهٔ جدید جایگزین می‌شود و به سرور می‌رود
  (سرور تضاد را برمی‌گرداند).

### ۴.۴. رابط و تنظیمات

- منوی سینی: «همگام‌سازی کمپین» → فرم `SyncForm`.
- فرم: فعال/غیرفعال، آدرس سرور، AgentId، Secret، تاریخ شروع، فاصله، اندازهٔ دسته، صف/خطا/شمارندهٔ دوره،
  دکمهٔ «همگام‌سازی فوری».
- کلید عامل با DPAPI کاربر ویندوز رمز می‌شود؛ متن ساده در `settings.xml` نوشته نمی‌شود.
- همگام‌سازی به‌صورت پیش‌فرض **خاموش** است؛ فعال‌سازی آگاهانه لازم است.
- پورت پیش‌فرض سرور و آدرس پیش‌فرض صندوق هم‌خوان شد: `http://…:5080`.

## ۶. محدودیت‌ها و ریسک‌های باقی‌مانده

1. **تطبیق ابطال فقط روز کاری جاری:** اگر فاکتوری فردای روز ثبت ابطال شود، صندوق آن را خودکار تشخیص نمی‌دهد.
   مسیر `void` مدیر وجود دارد، اما بازهٔ تطبیق چندروزه در فاز ۲ لازم است.
2. **بازگشت از `NeedsReview` خودکار نیست:** اگر فاکتور دوباره در منبع ظاهر شود، مسیر «تأیید مجدد» وجود ندارد.
3. **تکرارپذیری وااترمارک:** بر یکتایی و صعودی بودن `F_Code` تکیه دارد؛ در دادهٔ نمونه تأیید شد، اما پایش
   شکاف/تکرار در تولید لازم است.
4. **حجم و کارایی:** آزمون با ۱۶۰ فاکتور واقعی و ۱۰۰۰ رکورد سنتزی انجام شد؛ load test واقعی نشده است.
5. **HTTPS آزمون نشده:** E2E روی localhost و HTTP بود؛ TLS باید با reverse proxy و گواهی واقعی آزمون شود.
6. **بدون rate limit / WAF:** فقط HMAC و محدودیت اندازهٔ بدنه وجود دارد.
7. **رشد `IngestRequests` و `AuditLog`:** سیاست نگهداری/پاک‌سازی تعریف نشده است.
8. **حریم خصوصی موبایل:** شماره در دیتابیس کمپین به‌صورت قابل خواندن است؛ API آن را سانسور می‌کند،
   اما رمزنگاری/هش برای فاز ۲ تصمیم لازم است.
9. **تنظیمات محلی به کاربر ویندوز گره خورده است:** فایل `settings.xml` با DPAPI همان کاربر باز می‌شود؛
   جابه‌جایی فایل بین کاربران/سیستم‌ها نیازمند وارد کردن دوبارهٔ Secret است.
10. **رابط مدیریتی ندارد:** شروع/بستن دوره، تخصیص Held و ابطال فقط API است؛ پنل وب در فاز ۳ است.
11. **دورهٔ بعد خودکار باز نمی‌شود:** پس از تکمیل، اپراتور باید دوره را ببندد و دورهٔ بعد را باز کند.
12. **Held می‌تواند انباشته شود:** سیاست تخصیص خودکار تعریف نشده و عمداً صریح است.
13. **تنظیم امتیاز دو طرفه است:** `PointsPerAmountToman` سرور باید با تنظیمات صندوق هم‌خوان بماند؛
    عدم هم‌خوانی باعث اختلاف امتیاز نمایشی و سرور می‌شود.
14. **دو نسخهٔ فیزیکی:** تا زمان استقرار آگاهانه، نسخهٔ فعال قدیمی است و قابلیت همگام‌سازی ندارد.
15. **کلیدهای نمونه در `appsettings.json` حذف شدند:** سرور بدون تنظیم `Auth:AdminKey` و `Auth:Agents:*`
    مسیرهای مدیریتی/ingest را رد می‌کند؛ این رفتار عمدی و امن است.
16. **فاکتور غیرقابل‌ذخیره از وااترمارک عبور می‌کند:** برای جلوگیری از قفل‌شدن صف، خطای ذخیره در SQLite فقط لاگ
    می‌شود و کد بعدی ادامه می‌یابد؛ قرنطینه/هشدار برای این موارد در فاز ۲ لازم است.

## ۷. اجرا و استقرار (Runbook فاز ۱)

1. **پشتیبان:** از `posdiscount/bin/pos-discount.db` و `bin/settings.xml` نسخهٔ پشتیبان بگیرید.
2. **سرور:** دیتابیس `EbiCampaign` را بسازید (یا `AutoCreateDatabase` را فقط در توسعه true بگذارید)،
   `ConnectionStrings__CampaignDb`، `Auth__AdminKey` و `Auth__Agents__<id>` را تنظیم و سرویس را اجرا کنید.
3. **سلامت:** `GET /health` باید `ok:true` و `schemaVersion:1` بدهد.
4. **دوره:** با `POST /api/v1/admin/rounds/start` دورهٔ اول را باز کنید.
5. **صندوق:** در منوی سینی → «همگام‌سازی کمپین»، آدرس HTTPS، AgentId، Secret و تاریخ شروع را وارد،
   «فعال» را بزنید و ذخیره کنید. صف باید ظرف چند ثانیه خالی شود.
6. **کنترل:** شمارندهٔ دوره در فرم با سرور هم‌خوان باشد؛ فاکتورهای `Held` در پنل مدیر بررسی شوند.
7. **پایش روزانه:** صف/خطای همگام‌سازی، `Held`، و لاگ تطبیق (`sync reconcile`).
8. **بازگشت:** در صورت مشکل، تیک «فعال» را بردارید؛ نسخهٔ عملیاتی قدیمی و دادهٔ هلو دست‌نخورده‌اند.

## ۸. تصمیم‌های لازم برای فاز دو

| # | تصمیم | گزینهٔ پیشنهادی |
|---|---|---|
| ۱ | میزبان/دامنه/TLS سرور | reverse proxy (IIS/Caddy) + گواهی معتبر |
| ۲ | احراز هویت پنل مدیریت | کلید مدیر جداگانه یا SSO؛ عدم استفاده از کلید مشترک با صندوق |
| ۳ | توزیع و چرخش Secret هر صندوق | یک Secret مستقل برای هر دستگاه + چرخش دوره‌ای |
| ۴ | سیاست ابطال | بازهٔ تطبیق N روز + تأیید مدیر + مسیر «تأیید مجدد» |
| ۵ | سیاست Held | تخصیص دستی در فاز ۱؛ خودکار فقط با تأیید مدیر |
| ۶ | حریم خصوصی موبایل | رمزنگاری ستون یا هش برای جست‌وجو + نگهداری محدود |
| ۷ | نگهداری داده | پاک‌سازی `IngestRequests` پس از X روز و آرشیو `AuditLog` |
| ۸ | API خواندنی برای وردپرس | endpoint عمومی فقط‌خواندنی با CORS/نرخ محدود |
| ۹ | قرعه‌کشی | الگوریتم وزن‌دار با seed قابل حسابرسی و ذخیرهٔ خروجی |
| ۱۰ | پیامک/بله | صف مستقل + idempotency + لاگ تحویل |
| ۱۱ | پایش | متریک صف، نرخ خطا، تعداد Held، تأخیر ingest |
| ۱۲ | آزمون بار | شبیه‌سازی ۱۰۰۰+ فاکتور و چند صندوق هم‌زمان |
