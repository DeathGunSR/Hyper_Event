`Evidence` (شواهد تطبیق) پیش از هر تغییر خوانده و در تاریخچه ثبت می‌شود تا پس از تصمیم از بین نرود.

### بند ۵.۱–۵.۵ — موتور قرعه‌کشی قابل حسابرسی

| مورد | جزئیات |
|---|---|
| اسکیما | `migrations/004_lottery.sql` → `LotteryRuns`، `LotteryEntries`، ایندکس یکتای «فراگرفت فعال هر دوره»، تریگرهای تغییرناپذیری |
| موتور | `LotteryEngine.cs` — الگوریتم `ebi-lottery-weighted-v1` |
| سرویس | `LotteryService.cs` |
| مسیرها | تثبیت `POST /admin/rounds/{id}/lottery`، انتخاب `POST /admin/lottery/{id}/select`، نهایی‌سازی `.../finalize`، لغو `.../abort`، مشاهده `GET /admin/lottery` و `GET /admin/lottery/{id}`، سند `.../receipt`، راستی‌آزمایی `.../verify`، تماس با برنده `.../winner-contact` |

قواعد قطعی پیاده‌شده:

- هر فاکتور `Valid` دوره **یک ورودی مستقل** است؛ وزن هر ورودی = امتیاز همان فاکتور.
- ورودی با موبایل خالی ⇒ `no_mobile`؛ ورودی با امتیاز صفر ⇒ `zero_weight`؛ هیچ‌کدام وزن مثبت نمی‌گیرند،
  بنابراین «امتیاز صفر» به شانس تبدیل نمی‌شود.
- هر دوره فقط **یک برنده** دارد و برای هر دوره فقط یک فراگرفت فعال ساخته می‌شود
  (`UX_LotteryRuns_ActiveRound`؛ فراگرفت‌های لغوشده برای حسابرسی می‌مانند).
- **تعهد پیش از انتخاب**: Seed از `RandomNumberGenerator` (CSPRNG) ساخته می‌شود و `CommitmentHash`
  منتشر می‌شود؛ تا زمان انتخاب `seedHex` در هیچ پاسخ API نیست (`null`) و تنها پس از انتخاب افشا می‌شود.
- **تغییرناپذیری Snapshot**: تریگر `TR_LotteryEntries_NoUpdate` هر `UPDATE` روی ورودی‌های تثبیت‌شده را
  رد می‌کند و `TR_LotteryEntries_NoDelete` حذف دستی ورودی‌های یک فراگرفت موجود را می‌بندد.
- **تثبیت دو‌فازی با بازبینی پایداری**: مجموعه یک‌بار خوانده می‌شود، عضویت بله (در صورت نیاز) بررسی می‌شود،
  سپس در تراکنش `Serializable` مجموعه دوباره خوانده و هش پایداری مقایسه می‌شود؛ اگر تغییر کرده باشد
  `409 snapshot_unstable` برمی‌گردد و هیچ Snapshot نیمه‌ای ثبت نمی‌شود.
- **انتخاب اتمیک**: `UPDATE ... WHERE Status='Committed'`؛ چهار درخواست همزمان فقط یک برنده و یک رکورد
  حسابرسی می‌سازند (آزمون ۴۲).
- **بررسی مغایرت‌ها**: اگر فاکتور `NeedsReview` در دوره باشد، تثبیت بدون `acknowledgeReviews=true`
  با `409 unresolved_reviews` متوقف می‌شود؛ با تأیید آگاهانه، آن فاکتورها وارد مجموعهٔ قرعه‌کشی نمی‌شوند
  و شمارش تأییدشده در سند ثبت می‌شود.
- **بدون برندهٔ نامعتبر**: اگر عضویت بله تأییدنشده باشد (`bale_membership_unverified`) یا هیچ ورودی
  واجد شرایطی نباشد (`no_eligible_entries`) یا در زمان انتخاب مجموع وزن صفر شود (`zero_total_weight`)،
  فراگرفت در وضعیت `RequiresReview` می‌ماند و برنده ساخته نمی‌شود؛ `select` پاسخ `409` می‌دهد.

### موتور تصادفی — مشخصات بازتولیدپذیر

```
entriesHash  = sha256( concat( entryNo|invoiceId|fCode|mobile|points|eligibility|baleStatus , "\n" ) )
commitment   = sha256( "ebi-lottery-weighted-v1|round=<RoundNo>|entries=<entriesHash>|seed=<seedHex>" )
stream(c)    = HMAC-SHA256( key = seed , msg = "ebi-lottery-weighted-v1|round=<N>|entries=<H>|c" )
draw         = نخستین عدد یکنواخت در [0, totalWeight) از ردکردن نمونه‌های خارج از بزرگ‌ترین مضرب
                totalWeight (بدون سوگیری باقیماندهٔ تقسیم)
winner       = نخستین ورودی واجد شرایط که مجموع تجمعی وزنش از draw بگذرد
```

مسیر `GET /admin/lottery/{id}/verify` این سه چیز را بازمحاسبه می‌کند: هش مجموعه از دادهٔ فعلی، تعهد از
Seed افشاشده و برنده از Seed. مسیر `receipt` هم فرمول‌ها و گام‌های بازتولید را برای ممیز بیرونی برمی‌گرداند.
آزمون ۳۸ علاوه بر `verify`، برنده را مستقیم از سند عمومی (Seed + ورودی‌های واجد شرایط) بازتولید می‌کند.

### عضویت بله (ارائه‌دهندهٔ قابل‌جایگزینی)

- `IBaleMembershipProvider` با سه وضعیت `Member` / `NotMember` / `Unknown`.
- پیش‌فرض سامانه `UnconfiguredBaleProvider` است و صادقانه `unknown` برمی‌گرداند؛ `unknown` هرگز
  «عضو» تلقی نمی‌شود. عضویت در **زمان قرعه‌کشی** بررسی و در Snapshot ثبت می‌شود (وضعیت + شواهد + زمان).
- اجرای واقعی ربات بله **پیاده نشده است**؛ برای آن توکن ربات، شناسهٔ کانال و پیاده‌سازی همان واسط لازم است.

## ۳. تصمیم‌های طراحی که مالک باید بداند

1. **وزن = امتیاز همان فاکتور.** فرمول امتیاز سرویس (`PointsPerAmountToman`، مبنا `gross`/`net`) تغییر
   نکرده است؛ وزن قرعه‌کشی مستقیماً از همان امتیاز می‌آید تا دو منبع حقیقت نسازیم.
2. **شمارش تاریخی تغییرناپذیر است.** تصمیم‌های پس از تکمیل دوره، شمارندهٔ دورهٔ بسته را جابه‌جا نمی‌کنند،
   چون آن شمارنده مبنای اثبات تکمیل ۱۰۰۰ فاکتوری و سند قرعه‌کشی است.
3. **ورودی‌های بی‌موبایل شانس نمی‌گیرند** (نه به‌خاطر قانون، بلکه چون عضویت/تماس با برنده ممکن نیست).
   اگر مالک بخواهد این فاکتورها هم شانس داشته باشند، باید قانون جداگانه تصویب شود.
4. **تغییر نتیجهٔ نهایی‌شده بی‌صدا ممنوع است.** مسیر `force` نتیجه را عوض نمی‌کند، فقط وضعیت فاکتور را
   تغییر می‌دهد و فراگرفت را برای بازبینی انسانی علامت می‌زند.
5. **بازهٔ تطبیق (۴.۱)** با `ReconcileDays` (پیش‌فرض ۷)، `ReconcileIntervalMinutes` و
   `ReconcileConfirmations` تنظیم می‌شود و مغایرت تنها پس از چند مشاهدهٔ پیوسته به `NeedsReview` می‌رود.

## ۴. بازِ باقی‌مانده (پیاده‌نشده)

- **بند ۳.۳ — سیاست فاکتورهای ثبت‌شده در فاصلهٔ توقف دوره.** فعلاً در وضعیت انتظار (`Held`) می‌مانند و
  شمارش نمی‌شوند؛ انتقال فقط با تخصیص صریح مدیر (`POST /admin/held/assign`) انجام می‌گیرد. تصمیم نهایی
  مالک لازم است و رابط شروع دوره باید فهرست انتظار را نشان دهد (کار سمت رابط انجام نشده).
- **ربات بله.** فقط واسط ارائه‌دهنده ساخته شده؛ پیاده‌سازی واقعی نیازمند توکن ربات و شناسهٔ کانال است.
- **سامانه پیامک.** پیاده نشده. باید فقط با اقدام دستی و تأیید کاربر کار کند و پیش از انتخاب ارائه‌دهنده،
  گزینه‌ها بررسی شوند.
- **افزونهٔ وردپرس، پنل مدیریت وب و صفحهٔ عمومی کمپین.** پیاده نشده. پیش‌نیاز آن‌ها یک مسیر خواندنی عمومی
  (شمارنده، وضعیت دوره، برنده، تاریخچهٔ برندگان و تصاویر برندگان) است که هنوز ساخته نشده؛ فعلاً تنها مسیر
  عمومی `/health` است که کل وضعیت دوره را برمی‌گرداند و برای صفحهٔ عمومی کافی/مناسب نیست.
- **بارگذاری تصویر برندگان.** پیاده نشده.
- **محدودیت نرخ، WAF و آزمون بازیابی پشتیبان.** پیاده/سنجیده نشده.
