# آمادگی زیرساخت — سرویس کمپین EbiCampaign (بند ۴.۳)

این سند وضعیت واقعی سرویس مرکزی را برای استقرار مستند می‌کند. هر عددی که در آن آمده، از اجرای واقعی
آزمون بار روی همین مخزن گرفته شده است. مواردی که سنجیده نشده‌اند، به‌صراحت «سنجیده‌نشده» علامت خورده‌اند.

## ۱. محیط اندازه‌گیری

| مورد | مقدار |
|---|---|
| سیستم | Windows، تک‌نمونه، سرور و عامل روی همان ماشین (loopback) |
| Runtime | .NET 10 (`dotnet --version` → 10.0.402)، Build = Release از طریق `dotnet run` |
| پایگاه داده | SQL Server Express 17، دیتابیس آزمون `EbiCampaign_Test` |
| کلاینت | همان پروژهٔ آزمون (`EbiCampaign.Tests`) با `HttpClient` مشترک |
| تنظیمات دوره | `TargetInvoices=1000`، امتیاز ۱۰ per فاکتور ۵٬۰۰۰٬۰۰۰ تومانی |

دستورها:

```bash
export PATH="$HOME/.dotnet10:$PATH"          # مسیر SDK نصب‌شدهٔ .NET 10 روی این ماشین
cd Hyper_Event/server
EBI_LOAD=800x32  dotnet run --project EbiCampaign.Tests   # ۸۰۰ ارسال، همزمانی ۳۲
EBI_LOAD=1000x64 dotnet run --project EbiCampaign.Tests   # ۱۰۰۰ ارسال، همزمانی ۶۴
```

نتیجهٔ اطمینان‌بخش: **شمارندهٔ دوره زیر فشار همزمانی دقیق می‌ماند**. در هیچ اجرایی شمارنده از تعداد ارسال‌های
پذیرفته‌شده بیشتر یا کمتر نشد و هیچ درخواستی با خطای داخلی برنگشت.

## ۳. کاوش اشباع (یافتهٔ واقعی)

۴۰۰ درخواست `/health` با همزمانی ۲۰۰:

| اجرا | پاسخ ۲۰۰ | پاسخ ناموفق | زمان |
|---|---|---|---|
| ۸۰۰×۳۲ | ۳۰۹ | ۹۱ | ۸٫۰۴s |
| ۱۰۰۰×۶۴ | ۳۵۷ | ۴۳ | ۸٫۰۶s |

علت: هر فراخوانی `/health` دو پرس‌وجوی دیتابیس دارد و مخزن اتصال `Microsoft.Data.SqlClient` به‌طور
پیش‌فرض حداکثر ۱۰۰ اتصال همزمان می‌دهد. درخواست‌های اضافی در صف می‌مانند و پس از `Connect Timeout=8`
با استثنا برمی‌گردند؛ مسیر `/health` طبق طراحی آن را به `503` تبدیل می‌کند (نه ۵۰۰ و نه پاسخ اشتباه).

نتیجه‌گیری عملی:

- کاوشگرهای بار متعادل‌کننده و مانیتورینگ باید روی `/livez` و `/readyz` تنظیم شوند، نه `/health`.
- `/health` ابزار تشخیص انسانی است و نباید در حلقهٔ کوتاه کاوشگر قرار بگیرد.
- در استقرار واقعی `Max Pool Size` را با ظرفیت واقعی SQL Server و تعداد نمونه‌ها تنظیم کنید
  (مثلاً `Max Pool Size=200`)؛ در چند‌نمونه‌ای، مجموع مخزن همهٔ نمونه‌ها باید زیر سقف اتصال SQL بماند.
- اگر داشبورد/صفحهٔ عمومی به خواندن مکرر وضعیت دوره نیاز دارد، باید یک مسیر خواندنی با کش کوتاه‌مدت
  (۱–۵ ثانیه) بسازیم؛ فعلاً چنین کشی وجود ندارد و **اندازه‌گیری نشده** است.

## ۴. TLS و لبهٔ شبکه

- سرویس پشت reverse proxy با TLS اجرا شود (IIS/nginx/Caddy/Cloudflare Tunnel)؛ پورت `5080` فقط روی
  شبکهٔ داخلی یا loopback باز باشد.
- گواهی معتبر و زنجیرهٔ کامل؛ `HSTS` در لبه فعال شود.
- برنامهٔ صندوق باید `https://` بنویسد؛ امضای HMAC روی مسیر امضا می‌شود و از تغییر مسیر (redirect) بین
  `http` و `https` پرهیز کنید، چون مسیر در canonical امضا یکسان نمی‌ماند.
- **سنجیده‌نشده:** پین‌کردن گواهی در برنامهٔ صندوق پیاده نشده است؛ اعتبار گواهی به اعتماد سیستم‌عامل صندوق
  واگذار شده. اگر صندوق‌ها به CA داخلی وصل شوند، باید ریشهٔ گواهی روی همان ماشین نصب شود.
- محدودیت نرخ و WAF **پیاده‌نشده** است؛ برای مواجهه با اینترنت، محدودیت روی لبه تعریف شود.

## ۵. اجرای چند‌نمونه‌ای

معماری سرویس بدون حالت (stateless) است: هیچ نشست یا وضعیتی در حافظهٔ نمونه نگهداری نمی‌شود و همهٔ
تصمیم‌ها در دیتابیس کمپین گرفته می‌شود. بنابراین اجرای همزمان چند نمونه روی یک دیتابیس مجاز است،
به شرط رعایت این موارد:

| بخش | چند‌نمونه‌ای؟ | مبنا |
|---|---|---|
| ثبت فاکتور | ✅ | `UQ_Invoices_Source_FCode` + `UPDLOCK/HOLDLOCK` روی فاکتور و ردیف دوره؛ هر فاکتور یک بار شمرده می‌شود (آزمون ۱۲/۲۳/۴۴) |
| ابطال/تأیید مجدد | ✅ | تراکنش `Serializable` + قفل ردیف دوره |
| مسیر تصمیم مدیر | ✅ | قفل فاکتور و دوره + تاریخچهٔ افزودنی + `UX_Decisions_Key` برای ایدمپوتنسی |
| تثبیت قرعه‌کشی | ✅ | تراکنش `Serializable`، بازبینی دوبارهٔ مجموعه و `UX_LotteryRuns_ActiveRound` (برای هر دوره فقط یک فراگرفت فعال) |
| انتخاب برنده | ✅ | `UPDATE ... WHERE Status='Committed'`؛ آزمون ۴۲ نشان می‌دهد ۴ درخواست همزمان فقط یک برنده و یک رکورد حسابرسی می‌سازند |
| بررسی عضویت بله | ⚠️ | کش موقت در حافظهٔ همان نمونه است؛ هر نمونه ممکن است یک بار اضافه از ارائه‌دهنده بپرسد (بی‌خطر ولی تکراری) |
| کلید مدیر/عامل‌ها | ⚠️ | از پیکربندی/متغیر محیطی هر نمونه خوانده می‌شود؛ باید در همهٔ نمونه‌ها یکسان و از مخزن راز تزریق شود |

نکتهٔ عملیاتی: «شمارهٔ دورهٔ فعال» و «فراگرفت فعال» وضعیت مشترک دیتابیس‌اند؛ هر نمونه‌ای که درخواست مدیر
را دریافت کند همان نتیجه را می‌دهد. برای عملیات قرعه‌کشی توصیه می‌شود درخواست نهایی‌سازی از یک مسیر
مشخص (یک نمونه یا پشت قفل عملیاتی) ارسال شود تا ترتیب حسابرسی روشن بماند؛ نیاز به این کار با آزمون
اثبات نشده و یک توصیهٔ عملیاتی است، نه محدودیت فنی.

## ۶. پشتیبان‌گیری و بازیابی

دیتابیس `EbiCampaign` تنها منبع حقیقت است: فاکتورها، شمارندهٔ دوره، تاریخچهٔ تصمیم‌ها و سند قرعه‌کشی.

- پشتیبان کامل روزانه + پشتیبان گزارش تراکنش برای بازیابی نقطه‌ای (PITR).
- پیش از عملیات برگشت‌ناپذیر (تثبیت و انتخاب قرعه‌کشی، مهاجرت اسکیما) پشتیبان دستی گرفته شود.
- جداول `AuditLog`، `IngestRequests`، `InvoiceDecisions`، `LotteryRuns`، `LotteryEntries` هرگز پاک نشوند؛
  فقط `IngestRequests` قدیمی طبق سیاست نگهداری حذف شود (پاسخ‌های ایدمپوتنسی، نه سابقهٔ حسابرسی).
- پس از هر بازیابی، صحت سند قرعه‌کشی با `GET /api/v1/admin/lottery/{id}/verify` بررسی شود:
  بازسازی هش مجموعه، تطبیق تعهد با Seed افشاشده و بازتولید برنده. اگر این سه مورد سبز باشند، دادهٔ
  قرعه‌کشی دست‌نخورده بازیابی شده است.
- آزمون بازیابی (restore drill) **سنجیده‌نشده** است؛ باید روی یک دیتابیس کنار (staging) اجرا و مستند شود.

## ۷. پایش و هشدار

| مورد | ابزار | آستانهٔ پیشنهادی |
|---|---|---|
| زیست سرویس | `/livez` | هر پاسخ ناموفق در ۲ کاوش پیوسته |
| آمادگی وابستگی | `/readyz` | ۵۰۳ پیوسته بیش از ۳۰ ثانیه |
| سلامت تفصیلی | `/health` | فقط دستی/دوره‌ای |
| خطاهای ۵۰۰ | لاگ `unhandled error on {Path}` | هر رخداد |
| دورهٔ تکمیل‌شدهٔ بدون قرعه‌کشی | `GET /api/v1/admin/lottery` و `/api/v1/admin/rounds` | دورهٔ `Completed` بیش از یک روز |
| فاکتورهای بررسی‌نشده | `GET /api/v1/admin/invoices?status=NeedsReview` | وجود هر رکورد کهنه |
| فاکتورهای انتظار | `GET /api/v1/admin/held` | رشد پیوسته بدون شروع دورهٔ جدید |
| صف ارسال صندوق | گزارش صندوق (`Queue`) و `LastReconcileError` | هر خطای تطبیق |

## ۸. سخت‌سازی امنیتی

- `Auth:AdminKey` و کلید هر عامل، تصادفی و حداقل ۳۲ کاراکتر؛ خارج از مخزن و از مخزن راز تزریق شوند.
  تغییر کلید مدیر نیازی به بازنشر کد ندارد (متغیر محیطی + راه‌اندازی مجدد نمونه).
- کاربر دیتابیس فقط روی دیتابیس کمپین مجوز داشته باشد؛ هیچ دسترسی نوشتنی به `Holoo1` ندهید.
  سرویس هیچ اتصالی به هلو ندارد و نباید داشته باشد.
- اطلاعات شخصی: فهرست‌ها شمارهٔ موبایل را پوشانده برمی‌گردانند؛ شمارهٔ کامل فقط از مسیر
  `winner-contact` و با ثبت در `AuditLog` قابل دریافت است.
- سرورهای لبه باید فقط `/livez`، `/readyz`، `/health` و مسیرهای عمومی آینده (صفحهٔ کمپین) را بدون
  احراز هویت در دسترس بگذارند؛ مسیرهای `admin` از اینترنت بسته یا پشت احراز هویت لبه باشند.
